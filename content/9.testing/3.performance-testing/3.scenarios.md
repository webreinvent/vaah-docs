## Concepts Covered
1. **Scenarios** – Define different test flows and how they run concurrently within a test.
2. **Executors** – Specify the load pattern and behavior of virtual users for each scenario.
3. **Stages** – Configure ramping behavior by defining VU count over time for gradual load changes.
4. **HTML Report** - Generate comprehensive HTML report of your performance test executions.

## Scenarios
Scenarios in k6 enable you to specify different execution patterns for your virtual users. Each scenario can have its own configuration, including the number of VUs, execution duration, and the type of executor to use. This modular approach allows you to model complex user interactions and varying load conditions within a single test script.

### Benefits of using scenarios include:
- Easier, more flexible test organization. You can declare multiple scenarios in the same script, and each one can independently execute a different JavaScript function.
- Simulate more realistic traffic. Every scenario can use a distinct VU and iteration scheduling pattern, powered by a purpose-built executor.
- Parallel or sequential workloads. Scenarios are independent from each other and run in parallel, though they can be made to appear sequential by setting the startTime property of each carefully.
- Granular results analysis. Different environment variables and metric tags can be set per scenario.

### Example: Defining a Simple Scenario
To configure scenarios, use the scenarios key in the options object. You can give the scenario any name, as long as each scenario name in the script is unique.

Here's an example of how to define a basic scenario in k6:
::code-group
    ```bash [script.js]
    export const options = {
        scenarios: {
            example_scenario: {
                executor: 'shared-iterations',
                vus: 10,
                iterations: 100,
                maxDuration: '30s',
            },
        },
    };
::

In this example:
- `executor: 'shared-iterations'` specifies the execution strategy.
- `vus: 10` sets the number of virtual users.
- `iterations: 100` defines the total number of iterations.
- `maxDuration: '30s'` limits the test duration.

This configuration will run 10 virtual users, each executing 10 iterations, for a total of 100 iterations, within a maximum duration of 30 seconds.

## Executors
Executors control how k6 schedules VUs and iterations. The executor that you choose depends on the goals of your test and the type of traffic you want to model.

Define the executor in executor key of the scenario object. The value is the executor name separated by hyphens.
::code-group
    ```bash [script.js]
    export const options = {
        scenarios: {
            arbitrary_scenario_name: {
                // Name of executor
                executor: 'ramping-vus',
                // more configuration here
            },
        },
    };
::

### All Executor
| Executor Name          | Executor Key           | Description                                                      |
|-----------------------|-----------------------|------------------------------------------------------------------|
| [Shared iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/shared-iterations/)     | `shared-iterations`      | A fixed amount of iterations are shared between a number of VUs. |
| [Per VU iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/per-vu-iterations/)     | `per-vu-iterations`      | Each VU executes an exact number of iterations.                  |
| [Constant VUs](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-vus/)          | `constant-vus`           | A fixed number of VUs execute as many iterations as possible for a specified amount of time. |
| [Ramping VUs](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/ramping-vus/)          | `ramping-vus`            | A variable number of VUs execute as many iterations as possible for a specified amount of time. |
| [Constant Arrival Rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/) | `constant-arrival-rate`  | A fixed number of iterations are executed in a specified period of time. |
| [Ramping Arrival Rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/ramping-arrival-rate/)  | `ramping-arrival-rate`   | A variable number of iterations are executed in a specified period of time. |
| [Externally Controlled](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/externally-controlled/) | `externally-controlled`  | Control and scale execution at runtime via k6’s REST API or the CLI. |

To know more about each executor, click on the executor mentioned in the table above. This will take you to the official documentation for each executor.

## Stages
In k6, stages define the ramping pattern of virtual users (VUs) over time, allowing you to simulate changes in load during your test. They specify how the number of VUs should increase or decrease at specified intervals, helping mimic **real-world traffic** patterns such as ramp-up, steady-state, and ramp-down periods.

Each stage is represented as an object with two properties:
- **duration**: The length of time for which this stage runs (e.g., "30s", "2m", "10m").
- **target**: The target number of virtual users to reach by the end of this stage.

k6 automatically ramps the number of VUs from the current count to the target over the duration specified.

**Example of Stages configuration:**
::code-group
    ```bash [script.js]
    export let options = {
        stages: [
            { duration: '1m', target: 50 },  // Ramp up to 50 VUs over 1 minute
            { duration: '3m', target: 50 },  // Stay at 50 VUs for 3 minutes
            { duration: '1m', target: 0 },   // Ramp down to 0 VUs over 1 minute
        ],
    };
::

**Explanation:**
- The test starts with 0 VUs and ramps up to 50 over the first minute.
- It maintains 50 VUs for the next 3 minutes, simulating a steady load.
- Finally, it ramps down to 0 VUs over the last minute, gracefully ending the test.

**Notes:**
- Stages are mainly used with the `default` executor or the `ramping-vus` executor inside scenarios.
- Using stages is useful for testing how your system handles gradual increases and decreases in traffic rather than a sudden spike.\

## Examples

### Example 1: Load Test with ramping-vus Executor and Stages
::code-group
    ```bash [example1.js]
    import http from 'k6/http';
    import { check, sleep } from 'k6';

    export let options = {
        scenarios: {
            ramping_load: {
                executor: 'ramping-vus',    // Executor that supports stages
                startVUs: 0,
                stages: [
                    { duration: '30s', target: 50 },  // Ramp up to 50 VUs in 30 seconds
                    { duration: '2m', target: 50 },   // Hold 50 VUs for 2 minutes
                    { duration: '1m', target: 100 },  // Ramp up to 100 VUs in 1 minute
                    { duration: '3m', target: 100 },  // Hold 100 VUs for 3 minutes
                    { duration: '2m', target: 0 },    // Ramp down to 0 VUs in 2 minutes
                ],
            },
        },
    };

    export default function () {
        let res = http.get('https://test-api.k6.io/public/crocodiles/');
        check(res, {
            'status is 200': (r) => r.status === 200,
        });
        sleep(1);
    }
::

**Explaination**:
- `Scenario (ramping_load)`: Defines a named scenario for load testing
- `Executor (ramping-vus)`: Gradually increases and decreases the number of virtual users over time using stages
- `Stages`: A list that defines how many users should be active over specific durations
- `startVUs: 0`: The test starts from 0 virtual users
- `duration`: How long the stage lasts
- `target`: The number of VUs to reach by the end of the stage
- `sleep(1)`: Simulates realistic pause between user actions (think time)

**Use Case:** Simulates realistic user growth over time. Ideal for stress and soak testing.

### Example 2: Mixed Scenario with Different Executors
::code-group
    ```bash [script.js]
    import http from 'k6/http';
    import { sleep, check } from 'k6';

    export let options = {
        scenarios: {
            constant_users: {
                executor: 'constant-vus',     // Fixed number of VUs throughout
                vus: 30,                      // 30 users at all times
                duration: '5m',               // Run for 5 minutes
                exec: 'constantLoad',         // Use constantLoad function
            },
            ramping_requests: {
                executor: 'ramping-arrival-rate',  // Controls arrival rate (requests per second)
                startRate: 10,                     // Start with 10 iterations/sec
                timeUnit: '1s',
                preAllocatedVUs: 50,
                maxVUs: 100,
                stages: [
                    { duration: '1m', target: 50 },   // Ramp up to 50 req/sec in 1 min
                    { duration: '3m', target: 50 },   // Stay at 50 req/sec for 3 min
                    { duration: '2m', target: 0 },    // Ramp down to 0
                ],
                exec: 'rampedLoad',                // Use rampedLoad function
            },
        },
    };

    export function constantLoad() {
        let res = http.get('https://test-api.k6.io/public/crocodiles/1/');
        check(res, {
            'status is 200': (r) => r.status === 200,
        });
        sleep(1);  // Simulate user think time
    }

    export function rampedLoad() {
        let res = http.post('https://test-api.k6.io/public/crocodiles/', JSON.stringify({ name: "k6" }), {
            headers: { 'Content-Type': 'application/json' },
        });
        check(res, {
            'status is 201': (r) => r.status === 201,
        });
        sleep(0.5);
    }
::

**Explaination:**
1. **Scenario 1: constant_users**
   - Uses the constant-vus executor.
   - Keeps 30 virtual users active for 5 minutes.
   - Simulates a steady, consistent load.
   - Each user sends a GET request once per second.

2. **Scenario 2: ramping_requests**
   - Uses the ramping-arrival-rate executor.
   - Starts at 10 requests/second, ramps up to 50, holds, then ramps down to 0.
   - Focuses on request rate rather than the number of users.
   - Each iteration sends a POST request with a short sleep between.

## HTML Report
k6 provides a simple and visual way to view performance test results using an HTML Report. This is useful for sharing test outcomes with team members or storing them for historical tracking without needing external dashboards or integrations.

### How to Generate the HTML Report
To generate an HTML report for your test run, use the following command in your terminal:
```shell
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=test-report.html k6 run script.js
```
**Breakdown of the above commands:**
- **K6_WEB_DASHBOARD=true** : Enables the web-based (HTML) report feature in k6.
- **K6_WEB_DASHBOARD_EXPORT=test-report.html** : Sets the filename for the exported HTML report. You can change test-report.html to any name you prefer.
- **k6 run script.js** : Executes the k6 test script named script.js. Replace this with your actual script filename.

### After the Execution
Once the execution completes, a file named test-report.html will be created in your current directory.

You can open it in any web browser (Chrome, Firefox, Edge, etc.) to see a detailed and interactive dashboard of your performance test results.

### What’s Inside the Report?
The HTML report contains:

- **Summary Metrics**: Requests per second, average response time, error rates, etc.
- **HTTP Requests Breakdown**: by URL, status codes, and timings.
- **Trends Over Time**: latency, throughput.
- **Threshold Results**: if you’ve defined thresholds in your script.
